# Contributing to OmniCode-V

The canonical development rules live in [`AGENTS.md`](AGENTS.md). This file is
the human-oriented entry point; where the two could drift, `AGENTS.md` and the
guard scripts win.

## Setup

- Node 22 (see `.nvmrc`; `package.json` requires `>=22.19`).
- pnpm 12.5.1 (`corepack enable` picks it up from the `packageManager` field).
- TypeScript ESM monorepo: Turbo for builds, Vitest for tests, zod for
  validation.

```bash
pnpm install
pnpm dev:cli        # run the CLI against your working tree
```

Before editing, read the nearest guide: the root `AGENTS.md`, then the
`AGENTS.md` of the package or app you touch (see the read order in the root
guide), and `packages/README.md` for the package map. Code is the source of
truth.

## Checks

Guard and validation commands that exist in the root `package.json`:

```bash
pnpm check:guards       # workspace globs + kernel layering + docs claims + agent docs
pnpm typecheck          # turbo typecheck graph
pnpm --filter <pkg> typecheck
pnpm --filter <pkg> test
pnpm preflight          # runner: workspace check, guards, typechecks, targeted tests
```

While iterating, run the narrow check for what you touched rather than the
whole graph. The definition of done per change type (normal, CLI/TUI, memory,
package graph) is listed in `AGENTS.md` under "Definition of done"; report the
real result of whatever you ran.

Known command gaps — do not report these as meaningful validation:

- Root `pnpm lint` is a Turbo no-op (no package lint scripts exist).
- `apps/omnicode-cli` `test` / `e2e` scripts call a root script that does not
  exist. Run its Vitest directly:
  `pnpm --filter @omnicode/cli exec vitest run test/...`
- `packages/tui` uses `node --test`, not Vitest, and is outside the root Vitest
  run.

Generated manifests (`config-manifest.toml`, `wire-manifest.d.ts`,
`state-manifest.d.ts`) are regenerated by the owning scripts, never
hand-edited.

## Tests

- Tests live in `packages/<pkg>/test/` or `apps/<app>/test/`, mirroring `src/`.
  Prefer extending the nearest existing test file over creating a new one.
- Naming: `*.test.ts` unit/behavior, `*.integration.test.ts` integration,
  `*.e2e.test.ts` end-to-end. CLI e2e is gated behind `OMNICODE_E2E=1`
  (`OMNICODE_E2E_REAL=1` for live-provider runs).
- Provider tests use recorded HTTP cassettes; recording is opt-in with
  `OMNICODE_CASSETTE_RECORD=1`.
- Stub env with `vi.stubEnv()` in `beforeEach` / `vi.unstubAllEnvs()` in
  `afterEach`; unset a variable by stubbing it to `''`.
- Synchronize tests on explicit signals or observable state, never sleeps.
- Do not assert on source text or snapshots as a proxy for behavior.
- Guard tests are ordinary tests; printable keys and chalk colors are enforced
  in `apps/omnicode-cli/test/tui/`.

## Pull request expectations

- Enumerate the changed behavior, not only the changed lines. A refactor or
  port carries the old feature inventory — silently dropping a feature is a
  regression.
- A flipped default needs a named loss and an escape hatch.
- Prompt text is behavior. Contract files are tripwires: changing them changes
  the API.
- Bug fixes and behavior changes need a test that fails on the base and passes
  on the fix.
- Silent failure outranks a crash; do not weaken or bypass a guard to make a
  change land. Fix the underlying violation or state the blocker.
- Keep diffs focused. Scratch and handoff files go under `.tmp/` and are never
  staged.
- If you change a documented path, command, guard, or hard rule, update the
  nearest `AGENTS.md`.
- Describe validation honestly: name the commands you ran and their results. A
  skipped suite or an existing failure is not "green", and a GitHub Actions run
  only counts if it actually ran.
- Major releases and breaking API changes are not self-approved.

## Versioning

Versions are managed with changesets. Describe user-visible behavior in a
changeset alongside your PR; the flow is documented in
[`.changeset/README.md`](.changeset/README.md) and `docs/release.md`.
